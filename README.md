## Описание проекта
Проект разработан в рамках домашней работы №2 по дисциплине "Конструирование программного обеспечения" и представляет собой доменную модель классов приложения для учета финансов.

**HSE Bank** — это консольное приложение для управления банковскими данными пользователей, включающее функционал:
- создание, редактирование и удаление банковских счетов, категорий и операций;
- экспорт данных в формат JSON;
- импорт данных из JSON-файлов;
- визуализация информации в табличной форме (с помощью Spectre.Console);
- разделение на уровни (Domain, Application, Infrastructure, Presentation) с четкими зависимостями и внедрением зависимостей (DI).

Приложение построено по принципам **чистой архитектуры (Clean Architecture)**, что обеспечивает модульность, расширяемость и тестопригодность.

---

## Основной функционал

| Функция | Описание |
|----------|-----------|
| **Создание** | Добавление новых банковских счетов, категорий и операций в репозиторий. |
| **Редактирование** | Изменение свойств существующих объектов (например, названия счета или категории). |
| **Удаление** | Удаление объектов из хранилища. |
| **Экспорт** | Сохранение всех данных (счета, категории, операции) в отдельные JSON-файлы через шаблон **ExporterTemplate** и паттерн **Visitor**. |
| **Импорт** | Загрузка данных из JSON-файлов с помощью шаблона **ImporterTemplate** и посетителя **JsonImportVisitor**. |
| **Визуализация** | Отображение информации в консоли с помощью таблиц (**Spectre.Console**). |

**Примечание:**  
В папке `ExportedData` находятся тестовые данные, предназначенные для проверки корректности работы функции импорта.

## Архитектура

Приложение разделено на 4 уровня:

- **Domain** — бизнес-логика (сущности `BankAccount`, `Category`, `Operation` и интерфейсы `IEntity`, `IVisitor`);
- **Application** — реализация бизнес-процессов (экспорт, импорт, команды);
- **Infrastructure** — реализация хранилищ данных (`InMemoryRepository`, интерфейсы репозиториев);
- **Presentation** — пользовательский интерфейс (команды и обработка ввода).

Такое разделение уменьшает связность (**Low Coupling**) и повышает согласованность внутри модулей (**High Cohesion**).

## Принципы SOLID

| Принцип | Описание и реализация |
|----------|-----------------------|
| **S — Single Responsibility Principle** | Каждый класс выполняет только одну задачу. Например, `JsonExporter` отвечает только за экспорт данных, а `ExportJsonCommand` — за взаимодействие с пользователем. |
| **O — Open/Closed Principle** | Классы открыты для расширения, но закрыты для изменения. Добавление нового способа экспорта или импорта (например, XML) потребует создать новый класс, не изменяя существующие (`ExporterTemplate`, `ImporterTemplate`). |
| **L — Liskov Substitution Principle** | Любой конкретный экспортёр (`JsonExporter`) может подставляться вместо абстрактного (`ExporterTemplate`). |
| **I — Interface Segregation Principle** | Интерфейсы разделены на мелкие (`IExportVisitor`, `IImportVisitor`, `IRepository<T>`), чтобы классы реализовывали только нужную функциональность. |
| **D — Dependency Inversion Principle** | Верхние уровни зависят от абстракций, а не от реализаций. Например, `ExportJsonCommand` зависит от интерфейсов репозиториев, внедряемых через DI-контейнер. |

---

## Принципы GRASP

| Принцип | Реализация |
|----------|------------|
| **High Cohesion** | В каждом модуле сосредоточена логика одной ответственности. Например, `Application.Export` содержит только код, связанный с экспортом данных. |
| **Low Coupling** | Модули связаны через интерфейсы и внедрение зависимостей. Например, `ExportJsonCommand` не знает о конкретных реализациях репозиториев. |
| **Controller** | Команды (`ExportJsonCommand`, `ImportAllJsonCommand`) выступают контроллерами, координируя действия между слоями. |
| **Creator** | Репозитории создаются и управляются через DI-контейнер. |
| **Polymorphism** | Паттерн Visitor реализует полиморфизм при обработке разных типов сущностей (`BankAccount`, `Category`, `Operation`). |

## Использованные паттерны GoF

### Порождающие паттерны
| **Паттерн**                                       | **Реализация**                                                                                              | **Назначение**                                                                                                                                                                                                                              |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Template Method**                               | Классы `ExporterTemplate` и `ImporterTemplate`                                                              | Определяют общий алгоритм экспорта и импорта данных, делегируя реализацию конкретных шагов подклассам (`JsonExporter`, `JsonImporter`). Это позволяет избежать дублирования кода и упростить добавление новых форматов.                     |
| **Factory Method (через DI и отдельные фабрики)** | DI-контейнер в `Program.cs`, а также классы `BankAccountsFactory`, `CategoriesFactory`, `OperationsFactory` | Создаёт экземпляры экспортёров, импортёров и команд через контейнер зависимостей, а также централизует создание доменных сущностей (счетов, категорий, операций), инкапсулируя логику их инициализации и обеспечивая единообразие объектов. |



---

### Структурные паттерны
| **Паттерн**              | **Реализация**                                                                                | **Назначение**                                                                                                                                                      |
| ------------------------ | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Dependency Injection** | Настройка контейнера зависимостей в `Program.cs`                                              | Устраняет жёсткие зависимости между модулями, повышает модульность и тестопригодность системы.                                                                      |
| **Repository**           | Интерфейсы `IBankAccountsRepository`, `ICategoriesRepository`, `IOperationsRepository`        | Инкапсулирует доступ к данным, отделяя бизнес-логику от конкретного механизма хранения (в памяти, БД и т.д.).                                                       |
| **Decorator**            | `Presentation.Commands.Decorators.TimedCommandDecorator`                                      | Позволяет динамически расширять поведение команд без изменения их кода. Используется для измерения времени выполнения команд. Реализует принципы **OCP** и **SRP**. |
| **Facade**               | Классы `Application.Facades.*` (`BankAccountsFacade`, `CategoriesFacade`, `OperationsFacade`) | Объединяет работу нескольких репозиториев и фабрик, предоставляя единый упрощённый интерфейс для слоя Presentation. Снижает связанность между слоями приложения.    |

## Важность выбранных паттернов

В проекте реализовано **8 ключевых паттернов проектирования**, которые совместно обеспечивают модульность, расширяемость и поддержку принципов SOLID и GRASP.  

- **Template Method** — позволил создать единый шаблон для экспорта и импорта данных, где изменяются только детали формата (JSON и др.).  
- **Visitor** — обеспечил слабую связанность между структурами данных и операциями над ними (экспорт и импорт реализованы без изменения самих сущностей).  
- **Command** — изолировал обработку пользовательских действий, упростил добавление новых команд без изменения существующего кода.  
- **Repository** — отделил бизнес-логику от источников данных, обеспечивая возможность легко сменить реализацию хранилища.  
- **Dependency Injection** — упростил конфигурацию зависимостей, устранил жёсткие связи между модулями и повысил тестопригодность.  
- **Decorator** — позволил динамически расширять функциональность команд (например, добавлять измерение времени выполнения) без изменения их кода.  
- **Facade** — объединил работу с несколькими репозиториями в единые интерфейсы фасадов (`BankAccountsFacade`, `CategoriesFacade`, `OperationsFacade`), упростив взаимодействие между слоями.  
- **Factory Method** — централизовал создание доменных объектов (счетов, категорий, операций) через фабрики и DI, обеспечив единообразие и инкапсуляцию логики инициализации.
